# Internationalization (i18n)

The Potato OS web UI is multilingual. English (`en`) is the source of truth;
every other language is a JSON file of the same keys with translated values.
Adding a language is a documentation-sized change — no build step, no
dependencies — and is designed to be contributed directly by the community
via pull request.

## Languages shipped today

| Code | Language   | Status          |
|------|------------|-----------------|
| `en` | English    | Source of truth |
| `es` | Español    | Complete        |
| `fr` | Français   | Complete        |
| `pt` | Português  | Complete        |

Switch language from the selector at the top of **Settings**. The choice is
remembered in `localStorage` (`potato_lang`) and also persisted server-side
(`state/ui_preferences.json`, via `/internal/ui-preferences`) so it syncs
across devices. Resolution order on load: `localStorage` → server preference →
browser language → English.

## How it works

- **Engine:** `core/assets/i18n.js` — `t(key, {vars})` looks up the active
  locale, falling back to English per key, then to the key itself. Static
  markup is translated declaratively; dynamic strings call `t()` in JS.
- **Locales:** `core/assets/locales/<code>.json` — flat objects of
  `"namespace.key": "text"`. Namespaces group by area (`settings.*`,
  `addModel.*`, `runtime.*`, `field.*`, `mstatus.*`, `composer.*`, …).
- **Static markup** is tagged in HTML and hydrated on load / language change:
  - `data-i18n="key"` → element text
  - `data-i18n-placeholder`, `data-i18n-title`, `data-i18n-aria-label`,
    `data-i18n-alt` → the matching attribute
  - A label that wraps an `<input>`/`<select>` puts the text in an inner
    `<span data-i18n="…">` so hydration never removes the field.
- **Interpolation:** values may contain `{vars}`, e.g.
  `"Downloading {pct}%"`, filled at runtime via `t("key", { pct })`.

## Add or complete a language

1. **Scaffold** the file (values seeded from English, ready to translate):
   ```bash
   python scripts/i18n_locale.py new de
   ```
   (Or copy `core/assets/locales/en.json` to `<code>.json` by hand.) Keep every
   key; translate only the values.
2. **Register the code** in `core/assets/i18n.js`:
   - add it to `SUPPORTED`
   - add its native name to `LANG_NAMES` (e.g. `de: "Deutsch"`).
3. Preserve any `{vars}` exactly as they appear in English — the same names,
   in whatever order reads naturally in your language.
4. Leave brand names (Potato OS, Potato Chat, YAML, GGUF, PMIC…) untranslated.
5. **Check completeness** — a friendly per-locale report:
   ```bash
   python scripts/i18n_locale.py report
   ```
   or the CI gate itself:
   ```bash
   python -m pytest tests/unit/test_i18n_locales.py -q
   ```
   Both fail if your locale is missing keys, has unknown keys, or changed the
   `{vars}` of any string.
6. Open a pull request.

Partial translations are safe to ship: any key you leave in English (or omit)
falls back to English automatically, so the UI never breaks mid-translation.

## Right-to-left (RTL) languages

All shipped languages are left-to-right. The direction plumbing is in place:
`i18n.js` sets `<html dir>` from `dirFor(lang)`, driven by the `RTL_LANGS` set.
Adding a language like Arabic (`ar`) or Hebrew (`he`) to that set makes the
document flip to `dir="rtl"` automatically.

One step remains before an RTL locale looks right: the CSS still uses some
physical offsets. When adding the first RTL language, migrate them to logical
properties so the layout mirrors on its own:

- `margin-left` / `margin-right` → `margin-inline-start` / `-end`
- `padding-left` / `padding-right` → `padding-inline-start` / `-end`
- `left:` / `right:` on flow elements → `inset-inline-start` / `-end`
- `text-align: left/right` → `start` / `end`

Absolutely-positioned overlays (backdrops, dropdown anchors) usually don't need
changes. There is no RTL locale yet, so this is deferred, not blocking.

## Numbers and dates

`i18n.js` exposes `Intl`-based helpers bound to the active language:
`formatTime()` (runtime "Updated" timestamp) and `formatNum()` (localizes the
decimal separator — e.g. `6.370 W` → `6,370 W` in ES/FR/PT — with grouping
disabled so layouts stay stable). Byte units keep their English suffixes (GB,
MB) by design.

## Backend error codes

The backend already emits stable error *codes* (e.g. `insufficient_storage`,
`switch_failed`) rather than prose. The client translates them via the
`errcode.*` namespace and the `tReason(code)` helper, which falls back to the
raw code for anything it doesn't recognize. To localize a new backend code,
add an `errcode.<code>` key to each locale — no client logic changes needed.

Core (`core/` + `apps/`) emits stable codes for the user-facing failures it
owns — including `invalid_json` (malformed chat body) and
`terminal_session_limit` (web terminal) — which the client localizes via
`errcode.*`.

The **`inferno`** package (its LiteRT adapter) now emits codes too —
`litert_engine_not_loaded`, `invalid_json`, `messages_required`,
`vision_not_supported`, `inference_failed` — which the client reads from
`body.error.code` (`chat-engine.js::formatChatFailureMessage`) and localizes.
`vision_not_supported` routes to the text-only notice; the client also still
pattern-matches the legacy prose wordings as a fallback.

Those codes shipped in the `manuti/inferno` fork (see the `requirements.txt`
pin). Re-pointing the pin to upstream `potato-os/inferno` is the remaining
follow-up — runbook: [inferno-upstream-propagation.md](inferno-upstream-propagation.md).

## Coverage

The entire UI is localized — static markup and every dynamic string rendered
from JavaScript (status badge, download/update flow, runtime monitor, terminal,
chat composer, confirm dialogs, and platform notices). The only intentionally
untranslated text is brand names (Potato OS, Potato Chat) and technical tokens
(YAML, GGUF, PMIC, byte units, version strings).
